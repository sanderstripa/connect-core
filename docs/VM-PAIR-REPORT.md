# CONNECT Core: Windows → Linux, проверенный лабораторный VPN

Дата: 14 октября 2026 года. Ветка: `isolated-vm-network-stage`,
[PR #4](https://github.com/sanderstripa/connect-core/pull/4), без автоматического слияния.

Реализован сквозной срез существующего CONNECT IP v2: системный пакет Windows
проходит через Wintun, собственный формат CONNECT, QUIC DATAGRAM с TLS 1.3/mTLS,
Linux TUN и маршрутизацию ядра Linux до отдельного лабораторного сервиса.
Ответ возвращается тем же путём. Xray, Sudoku и MIST как промежуточные процессы
в этой цепочке не участвуют. Архитектура и формат v2 сохранены; локальный TCP v1
остаётся совместимым.

## Что фактически проверено

Опорный успешный прогон:
[Actions 38544707842](https://github.com/sanderstripa/connect-core/actions/runs/38544707842),
коммит `10668578202caf78183f545a84a1664aac927aac`. Полные результаты и захваты доступны в артефакте
`windows-linux-vm-results` этого прогона. Это Windows VM GitHub Actions и отдельная
Linux VM внутри неё, запущенная QEMU в режиме программной эмуляции. У Linux
собственное ядро и настоящие TUN/сетевые пространства имён; эмуляции успешного
соединения нет. Две VM на независимых физических хостах не испытывались.

| Испытание | Фактический результат |
|---|---|
| HTTP через системную маршрутизацию | Ответ и контрольная полезная нагрузка проверены |
| Двоичный TCP, half-close, эхо 1 MiB | Побайтовая проверка хеша и завершения |
| UDP | 100 последовательных обменов и параллельные серии |
| 1, 8, 32 TCP и UDP | Все серии прошли до и после восстановления; барьер удерживает одновременно открытыми все N сокетов |
| DNS | UDP/53 и Windows `getaddrinfo` для уникального имени `.test` через Linux |
| Неверная идентичность сервера | Отказ до создания дополнительного Wintun |
| Клиентский сертификат от чужого CA | Отказ до создания дополнительного Wintun |
| 100 некорректных UDP-пакетов транспортному порту | Сервер продолжил работу; дальнейшее восстановление и трафик прошли |
| Принудительная остановка и запуск Linux Core | Состояние reconnecting, сохранение Windows-интерфейса, свежая mTLS-сессия, повтор всех серий |
| Отключение виртуальной сетевой карты Linux при живом сервере | Отказ трафика без обхода; после включения новая сессия и повтор всех серий |
| Принудительное завершение Windows Core | TCP/UDP/DNS сервиса недоступны, прямые обходные пробы неуспешны |
| Локальный IPC | Ответ status с настоящими счётчиками пакетов |
| Откат | Журнал rolled-back; принадлежащие стенду firewall/NRPT-правила отсутствуют |

32 здесь означает прикладные соединения одного устройства, а не 32 одновременно
аутентифицированных устройства. Один полный цикл остановки/восстановления сервера
и отдельный цикл разрыва/восстановления виртуальной сети проверены на VM;
дополнительные повторные сессии проверяются существующими тестами
ядра. Обычный Windows/Linux CI также выполняет тесты, race, fuzz, vet и сборку.
Неверные ключи, CA, ALPN, повреждённые IP/control-пакеты и нарушения сетевой
политики проверяются отдельными тестами ядра; не все эти случаи повторены на VM.

## Захваты и защита от обхода

Linux: 21 134 кадра — 21 119 пакетов UDP защищённого endpoint, шесть ARP и девять ICMP.
Адреса транспортных IP-пакетов ограничены парой 10.0.2.2/10.0.2.15; незашифрованный
контрольный текст и DNS-вопрос отсутствуют в 160-байтовых снимках пакетов.
Это проверка заголовков и начала полезной нагрузки, не полный дамп всех шифротекстов.
SHA-256 полученного PCAP совпал с хешем исходного файла в Linux-госте:
`b15a6c0980c345a14f28120ce024bb42c4aa5c62eb760daabeb543916f626146`.

Windows: отдельно экспортированы компоненты Wintun, Mellanox NIC и NetVsc.
На Wintun захвачены 16 581 TCP и 970 UDP пакетов. На альтернативных
интерфейсах не обнаружены лабораторные IP/данные/DNS, прямые пробы или исходящие
TCP/UDP-данные. На Mellanox NIC присутствовали 32 входящих фоновых TCP-пакета с данными,
шесть входящих служебных TCP-пакетов и четыре кадра не-IP. Это входящий фоновый трафик
самой CI VM, а не исходящая передача через обход VPN; он не скрыт из отчёта.
Полной тишины физической сети не заявляется. Верификатор также отказывает при
исходящем UDP, неизвестном/VLAN/фрагментированном формате и неподдерживаемых IPv6-данных.

Более ранняя строгая проверка обнаружила последний пакет уже открытой фоновой
TCP-сессии после установки firewall-правил. Проверка была признана неуспешной.
Исправление: до активации сетевого плана завершать внешние IPv4 TCP-сессии через
Windows SetTcpEntry и повторно проверять их отсутствие. В опорном прогоне в
журнал попали 10 таких соединений. Их восстановление откатом невозможно; этот
приём допустим только в одноразовом стенде. Основной Windows-компьютер не затронут.

Прямая IPv4 TCP-проба получила WSA 10013, внешняя UDP DNS-проба не получила ответа;
захваты отдельно подтвердили отсутствие этих запросов на обходных NIC. IPv6-проба
получила WSA 10051: у стенда отсутствует внешний IPv6-маршрут. Общая блокировка
IPv6 установлена, но обход при наличии работающего внешнего IPv6 не доказан этим
стендом и остаётся отдельным испытанием. На Linux IPv6 отключён в лабораторных
пространствах имён; формат CONNECT v2 принимает только поддерживаемый IPv4.

## Какие механизмы использованы

От MIST применим принцип IP-пакетов поверх datagram-транспорта с отдельным
надёжным управлением; здесь используется собственный CONNECT v2, а не копия
HTTP/3 CONNECT-IP. От актуального Xray полезны принципы TUN, разграничения
маршрутизации/пакетного движка, ограничений исходящего пути и MTU; реализация
самостоятельная. Код и криптография Sudoku не переносились. Его маскировка не
объявляется доказательством криптографической безопасности.

Защиту обеспечивают проверенные реализации TLS 1.3/QUIC, mTLS, закрепление
клиентского сертификата, привязка сертификата к адресу и строгая политика
источника/назначения. Новых криптографических алгоритмов нет. Маскировка, REALITY,
XHTTP, Sudoku-кодирование и каскад движков не реализованы. Это не независимый
криптографический аудит. [Исследование](IMPLEMENTATION-AUDIT.md) с Xray v26.10.10
и [решения/лицензии](DECISIONS.md) сохранены; исходники чужих движков не копируются.

## Ограничения и следующий этап

Это VPN к разрешённому частному сервису 10.232.0.1/32, не общий интернет-VPN.
Нет NAT в интернет, общего default route, рекурсивного внешнего DNS, проверенного
DNS-over-TCP, IPv6-туннеля, фрагментов/PMTU, маскировки, транспортного fallback,
проверки потерь сети/UDP-блокировки, 1h/24h нагрузки и 32 отдельных устройств.
Нет производственного WFP-сервиса, восстановления после перезагрузки, защиты
журнала от другого привилегированного процесса и поддержки смены NIC во время
работы. Не испытывались аварии самого механизма отката. Такой сбой требует
сохранить журнал и удалить одноразовую VM, не объявлять сеть восстановленной.

CONNECT./CONNECT UI получают перспективу интеграции через наследуемые локальные
каналы status/stop, версию IPC и реальные счётчики. Готовый UI-адаптер этим PR не
поставляется. Engine ready означает подтверждённую сессию и интерфейс; UI должен
дополнительно проверять активный сетевой журнал и работоспособность туннеля.

Следующий этап — независимые VM/стенд с маршрутизируемым IPv6, отдельный устойчивый
сетевой контроллер с защищённым журналом и восстановлением после перезагрузки,
полноценный DNS и длительные/искажённые сетевые испытания. Реальный VPS требует
отдельного разрешения. Амстердам, датские Xray/Sudoku/MIST и маршруты/DNS/firewall
основного Windows-компьютера не изменялись. [Инструкция стенда](VM-PAIR.md).
