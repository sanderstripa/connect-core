# Architecture and validation plan

## Boundary and first milestone

**CONNECT Core** owns client/server runtime, lifecycle, policy, stream forwarding,
configuration, bounded resource use, adapters and metrics. **CONNECT Protocol**
specifies interoperable requests and replies. An engine release may change
without a wire-format change. Config, protocol and adapter versions are distinct.

The original milestone is local TCP forwarding to a fixed allowlisted test
service. The next implemented slice is CONNECT IP v2: native isolated IPv4 TUN,
QUIC datagrams, mTLS device/address bindings and narrow destination policy.
See [concrete decisions](DECISIONS.md), [IP lab](IP-LAB.md) and
[actual validation](VALIDATION.md). Installer/panel and full-device networking
remain future stages.
It uses standard-library TLS 1.3, not an original crypto design. Certificates are
Ed25519-signed lab certificates; TLS negotiates its supported authenticated
encryption and ephemeral key exchange internally.

## Roadmap beyond the isolated IP slice

1. Keep protocol parsing, destination policy and transport dialers independent.
   A future `StreamDialer` returns a stream; a `DatagramSession` is a different
   interface with MTU, drop and ordering semantics. Do not force IP packets onto
   reliable streams without measuring head-of-line blocking and TCP-over-TCP.
2. Add SOCKS5 as a frontend with remote destination resolution; add a separate
   policy-checked destination opening command only in a new explicit protocol
   revision. Today the service-ID format avoids open-proxy and DNS-rebinding risk.
3. Add managed Xray, Sudoku and Mist adapters as optional pinned subprocesses.
   Each reports capabilities (TCP, UDP, IP, IPv6, client identity, cancellation).
   They retain their own protocol formats/configuration, and do not carry CONNECT
   bytes until a compatible transport bridge actually exists. Existing clients
   cannot speak the new wire format without a new adapter or updated executable.
4. Maintained QUIC datagrams now carry IPv4 with bounded queues, MTU and
   anti-spoof policy. Direct TCP flow multiplexing over QUIC streams remains
   optional future work. Add HTTP/2 only after defining real tunnel behavior. QUIC
   and HTTP/2 availability are not guarantees of resistance to filtering.
5. Linux namespace TUN and Windows Wintun code are now present; cross-OS VM
   validation remains a required stage. The elevated route/DNS/firewall helper is separate from the ordinary
   user's engine and UI. Establish endpoint bypass routes before full tunneling,
   journal changes and roll back on interruption. IPv6 must be tunneled correctly
   or explicitly blocked; never leave it as a silent direct fallback.
6. Device authentication uses independent credentials; revocation must close
   active sessions and persist across restart. Lab policy today is restart-only.
   Keep runtime management on a permission-protected local socket/pipe. A panel
   comes later with independently secured authentication, CSRF and update policy.

## Configuration and compatibility

Use a versioned strict schema with separate sections for frontend, engine,
transport, trust/identity, destination policy, routing/DNS and observability.
Secrets should be file references with platform-appropriate permissions or OS
credential storage. Never bundle real keys, print credentials or store them in
benchmark artifacts. Current minimal JSON is generated by `init-lab`; it uses
absolute certificate paths and explicit service allowlists.

Engine adapters validate inputs rather than passing arbitrary executable paths or
shell arguments from profiles. Capability negotiation must never silently weaken
trust or select a direct route. Unsupported operations/versions fail closed.
Record dependency revisions and checksum-verified binaries; test profile import
against both generated configs and running engines. Do not rename VLESS/XHTTP,
Sudoku or Mist profiles to CONNECT Protocol.

## Test gates

| Gate | Method and acceptance |
| --- | --- |
| Vertical flow (implemented) | Real HTTP through local forwarder, TLS/mTLS and server; exact response body |
| Byte correctness (implemented) | Eight simultaneous clients, binary payload equality and half-close |
| Authentication (implemented) | Wrong CA/name, expired server, missing certificate, disallowed leaf, wrong ALPN rejected |
| Parsing/policy (implemented) | Oversized/truncated/unknown wire requests rejected; unknown service rejected; external addresses rejected |
| Lifecycle (implemented) | Cancellation closes active connection and joins listener handlers; 100 independent connections complete |
| Latency/throughput smoke (implemented) | p50/p95/p99 64-byte loopback echo RTT and 64 KiB echo benchmark; no speed promises |
| Fuzz/races | Native fuzz parser for 10 seconds locally; `-race` on Windows/Linux CI; verify actual CI results separately |
| Network performance (planned) | Dedicated lab VMs: direct baseline and each engine under identical CPU/MTU/concurrency; useful bytes/s, setup time, RTT percentiles, CPU/RAM and drops |
| Impaired networks (planned) | netem 20/80/200 ms RTT, 0/1/3% loss, bandwidth caps, reordering, MTU changes and UDP blackout; collect failures and recovery time |
| Stability (planned) | 1 h then 24 h soak, 1/8/32 clients, slow readers, idle sessions, server restart, revocation, suspend/resume; bounded memory/goroutines and clean shutdown |
| Full VPN leaks (planned) | Packet captures on physical interface for IPv4/IPv6/DNS/UDP/WebRTC during connect, disconnect, core crash, endpoint failure and sleep/resume; only allowed endpoint/control traffic in full-tunnel mode |

The first benchmark is local and counts round-trip bytes, excludes handshake and
contains no impaired-network test. Repeat under documented hardware and topology
before comparing results. Coarse host timers can produce a zero-duration sample;
that is measurement resolution, not zero network latency. Define per-environment
budgets after measuring a direct
baseline; do not invent throughput/latency targets beforehand. Fixed correctness,
authentication and leak expectations should pass without tolerance.

## Infrastructure safety

No Amsterdam access, installers, system services, port 443, host NAT, host firewall,
production certificates or existing profiles were changed. Legacy v1 rejects
non-loopback infrastructure; v2 accepts numeric private lab endpoints and narrow
private destination policies, with explicit isolation restrictions. Real deployment requires a separately
selected disposable VM/VPS, credentials and ports, plus explicit authorization
for concrete changes. Prefer a new host rather than the production VPN host.
Keep lab certificates and address ranges separate. Take a snapshot before TUN
tests; retain rollback and packet captures. Lab support is not authorization
to deploy to a real server or a production configuration.

The next isolated stage adds a managed client owning one native interface across
fresh QUIC sessions, private inherited-pipe control, and a separate journaled
Windows CI network helper. The engine still does not edit workstation routes,
DNS or firewall rules. The helper is available only in an opted-in disposable
CI VM and retains persistent guards across Core crashes. See
[VM-PAIR.md](VM-PAIR.md) for topology, failure boundaries and evidence gates.
